# 个人 BI Agent 能力演进路线图

> 状态：**draft（待评审）** · 基线：v0.1.0（2026-11-03 差距分析产出）
> 产品文档源头维护在 DocMind `openui-analytics` 项目同名节点；本文件为仓库镜像，随代码演进同步。

## 0. 文档定位

基于 2026-11-03 的能力差距盘点，规划产品从「对话式看板生成器」演进到「个人 BI Agent」的路径。与既有规划的关系：

- **继承**：DocMind「个性化场景分析」节点已规划的 P2（业务理论包与语义层）、P3（个人语境）方向不变，收编为本路线图 P2-B / P3-C
- **新增**两根主线：**活看板**（查询与渲染分离）与 **Agent 主动性**（订阅与告警）——这是差距分析中「BI 本质缺位」与「Agent 定义性能力缺失」的补齐

## 1. 现状基线（v0.1.0 已具备）

| 能力 | 状态 |
| --- | --- |
| 对话式分析 → 声明式看板（19 组件，流式渲染） | ✓ |
| 多路数据源（PG / GitLab / 禅道 / CSV·Excel→DuckDB / 动态 MCP） | ✓ |
| Plan-first 两阶段（思路确认 → 执行） | ✓ |
| 方法论库（10 内置卡 + 用户 JSON 卡，三级扩展） | ✓ |
| 看板收藏 / 快照导入导出 / 重新分析 | ✓ |
| 存储：服务端 JSON 文件 + 浏览器 localStorage，零数据库 | ✓ |

## 2. 目标画像：什么叫「个人 BI Agent」

五个维度定义完整形态，当前只满足前半：

| 维度 | 含义 | 现状 |
| --- | --- | --- |
| **活数据** Live | 看板绑定查询而非快照，数据可独立于 LLM 刷新 | ✗ 快照 |
| **懂业务** Semantic | 指标口径、实体映射、业务术语沉淀复用 | ✗ 每次重新解释 |
| **主动** Proactive | 定时分析、指标监控、主动推送 | ✗ 纯被动问答 |
| **记得住** Memory | 个人语境、偏好、常用问题跨设备延续 | ✗ localStorage 失忆 |
| **深度自主** Autonomy | 多轮自主任务编排、分析资产沉淀 | △ 仅 plan→execute 两步 |

## 3. 差距总览（2026-11-03 盘点结论）

1. **主动性缺失**：无调度器/订阅/告警/推送渠道（最大差距）
2. **看板是快照**：dsl 存渲染结果，数据停在生成时刻；刷新 = 重跑 LLM
3. **记忆与语义层未落地**：无口径定义/实体映射/个人语境；会话困在 localStorage
4. **跨源只有特例**：crossSourceMap 是手工禅道→GitLab 点映射，无联邦查询
5. **自主任务深度不足**：无 agent loop、无分析资产库
6. **工程配套**：远程访问薄弱、无成本缓存

## 4. 分期规划

### P2 活看板与语义层 —— 从「生成器」到「BI」的分水岭

#### P2-A 看板查询重放（查询与渲染分离）⚠️ 最高优先

> 进度：**① 数据模型与生成期捕获已落地**（2026-11-03，`src/lib/dashboardStore.ts` + `src/lib/dashboardCapture.ts`，收藏链路自动捕获 queries/bindings，旧快照兼容）；**② 刷新 API 与降级语义已落地**（2026-11-03，`src/lib/dashboardRefresh.ts` + `POST /api/dashboards/[id]/refresh`，零 LLM 重放回填，stale 组件级降级）；**③ UI 与 P2-A 收口已落地**（2026-11-03，`DashboardPreviewModal` 头部「刷新数据」按钮 + `dataUpdatedAt` 时间戳 + stale 组件过期徽标，`useDashboards.refreshOne(id)` 走 refresh 端点，收藏列表摘要透出数据时间；刷新按钮态/时间戳/stale 徽标/旧快照禁用均有组件测试固化）。**评审加固（2026-11-04）**：tool 重放服务端只读白名单（写语义工具拒绝重放，queries 视为不可信落盘数据）；全部查询重放失败 → replay-failed 整体失败不落盘（502）；重放失败逐条告警留痕；预览刷新 catch 兜底 + 迟到回写 id 匹配守卫。P2-A 全段完成。

**问题**：`DashboardRecord.dsl` 是渲染快照字符串；打开旧看板数据停留在生成时刻；「重新分析」重跑整轮 LLM（贵、慢、结果漂移）。

**目标**：收藏看板可**不经过 LLM** 一键刷新数据，数值随源更新。

**技术方案**：

1. **数据模型扩展**（`DashboardRecord` 增加可选字段，旧快照天然兼容）：

   ```ts
   interface DashboardQuery {
     id: string;                 // q_ 前缀
     sourceId: string;           // 数据源 id
     kind: "sql" | "tool";       // db 类源重放 SQL；MCP 类源重放工具调用
     payload: string;            // SQL 文本 或 { tool, args }
   }
   // record 增加：
   queries?: DashboardQuery[];
   bindings?: Record<string, string>;   // DSL 组件 id → query id
   dataUpdatedAt?: number;              // 最近一次刷新成功时间
   ```

2. **生成期捕获**：execute 轮工具调用完成后，将「被看板组件直接引用的取数查询」记录进 bindings。**只绑定直取数组件**——LLM 加工过的数据（计算列、合并结果）不可重放，组件标记 `derived` 不参与刷新。

3. **刷新链路**：`POST /api/dashboards/[id]/refresh` → 服务端按序重放 queries → 数据回填 dsl 组件 → 更新 `dataUpdatedAt` → 返回新 dsl。无任何 LLM 调用。

4. **降级语义**：单查询失败 → 该组件保留旧数据 + 前端「过期」徽标；源不可用 → 刷新整体失败并提示；旧快照无 queries → 维持只读现状不报错。

5. **UI**：看板预览头部加「刷新数据」按钮 + 数据时间戳展示。

**验收**：
- 收藏看板刷新后数值更新，网络面板确认零 LLM 调用
- 含 derived 组件的看板：直取数组件刷新、derived 组件保留并标注
- 导入 v0.1 旧快照不报错（无 queries 字段走只读路径）
- 刷新失败降级路径有测试覆盖

**风险与边界**：SQL 重放依赖源 schema 稳定（列改名即失效）→ 失败信息里给出「重新分析」引导；刷新只保证数值新鲜，不保证叙事文本（标题/洞察仍是生成时快照）。

#### P2-B 业务理论包与语义层（承接 DocMind 既有 P2 规划）

- **指标口径**：GMV / LTV / DORA 等口径定义，存储 `data/semantic/`（与看板库同模式）
- **实体映射**：用户标注「哪张表是订单表、哪个字段是日期/渠道/金额」→ 方法卡与口径自动套用
- **业务包**：研效四预设场景收编为首个业务包；业务包自带方法卡经 registry 注入
- **用户方法卡编写 UI**（替代手写 JSON）
- 详细设计另立 DocMind 节点（既有约定）

### P3 Agent 主动性 —— 从「BI」到「Agent」的入场券

#### P3-A 订阅式定时分析

**目标**：「每天早 9 点给我昨日经营日报」类需求成立。

**技术方案**：

1. **任务模型**：

   ```ts
   interface Subscription {
     id: string; name: string;
     schedule: string;           // cron 表达式（自然语言周期在创建时由 LLM 转 cron）
     prompt: string; sources: string[];
     delivery: { channels: string[] };  // 见 P3-B 渠道抽象
     enabled: boolean; lastRunAt?: number; nextRunAt: number;
   }
   ```

2. **存储**：任务 `data/subscriptions/*.json`；**运行历史引入 SQLite**（better-sqlite3）——追加型数据（每次运行一条）不适合 JSON 全量重写，这是「零数据库」原则的第一个让步点，决策见 §5 工程基座。

3. **调度**：进程内简易调度器（轮询 `nextRunAt`，单机单实例假设，不做分布式）；服务重启恢复 `nextRunAt` 已过期任务补跑一次。

4. **执行**：复用 analyze handler（direct 模式）脱离 UI 跑批；产物看板自动入收藏库并关联订阅 id。

5. **UI**：侧边栏「订阅」入口；任务 CRUD；运行历史列表（成功/失败/产物链接）。

**验收**：创建 cron 任务到点自动执行并产出看板；失败任务在历史中可见且可重试；重启后调度恢复。

#### P3-B 指标监控与告警

**目标**：盯住核心指标，越界/异动主动触达。

**技术方案**：

1. **规则模型**：

   ```ts
   interface WatchRule {
     id: string; name: string;
     metric: { sourceId: string; query: DashboardQuery };  // 复用 P2-A 查询模型
     condition:
       | { kind: "threshold"; op: ">" | "<" | ">=" | "<="; value: number }
       | { kind: "anomaly-zscore"; z: number };            // 复用 anomaly 方法卡基线思想
     window: string;             // 检查周期（复用 P3-A 调度器）
     channels: string[];
   }
   ```

2. **探测执行器**：复用 P2-A 查询重放——告警检查就是「定时跑一个查询 + 判条件」，**P2-A 是本项硬前置**。

3. **通知渠道抽象 `Notifier` 接口**：P3 先落地 **webhook**（通用，可接企业微信/飞书/钉钉 bot）+ **站内通知中心**（侧边栏铃铛）；邮件后置。

**验收**：阈值规则触发后 webhook 收到含指标值的 payload；站内通知可跳转产出的看板；规则暂停/恢复生效。

#### P3-C 个人语境（承接 DocMind 既有 P3 占位）

- 偏好沉淀（默认布局/图表风格）、常用问题推荐、术语自动学习
- **存储迁移**：个人画像从 localStorage 迁至服务端 `data/profile/`（跨设备的第一步；会话云同步可顺此路径推进，解决换浏览器失忆）

### P4 深度与规模（方向性占位，启动前另立详细设计）

| 项 | 方向 | 关键点 |
| --- | --- | --- |
| P4-A 跨源联邦查询 | crossSourceMap 通用化 | 实体对齐配置 + LLM 编排多源查询的稳定契约；避免自研 join 引擎 |

## 5. 工程基座（横切决策）

| 决策点 | 结论 | 理由 |
| --- | --- | --- |
| 数据库引入时机 | P3-A 运行历史引入 better-sqlite3（嵌入式，无服务进程） | 配置类数据继续 JSON；只有追加型数据值得上 SQLite；保持零外部依赖部署 |
| 单机单实例假设 | 保持 | 个人 BI 定位；调度器与存储均不做并发/分布式设计 |
| 存储分层原则 | 配置=JSON 可手编；记录型=SQLite；缓存=进程内 | 沿用现有「文件优先」哲学，按数据形态分层 |
| 测试基线 | 延续现有模式（路由接缝 mock + 组件测试 + 快照守护），全量绿为准 | 当前 57 文件 / 456 测试 |

## 6. 里程碑与依赖

```
P2-A 活看板(≈1.5–2周) ──→ P3-B 告警(≈1–1.5周)
        │                      ↑ 硬前置（探测=查询重放）
        └→（并行）P2-B 语义层(≈2–3周)
                 ↓
P3-A 订阅(≈1.5–2周) ──→ P3-C 个人语境(≈1周)
                          ↓
                    P4 按需启动
```

**关键路径**：P2-A → P3-A → P3-B。P2-A 既是「BI 分水岭」又是告警的地基，是全局最高优先。

## 7. 风险与取舍（明示不做的事）

- **不做多用户/云端化**：个人单用户前提贯穿 P2/P3；多用户引入需重开存储与鉴权设计
- **不做分布式调度**：单进程内调度，重启补跑一次为上限
- **刷新不重写叙事**：数据刷新只更新组件数值，洞察文本仍是生成时快照——「数据新鲜」与「叙事新鲜」分离，后者仍走重新分析
- **快照兼容优先于能力**：任何 record 扩展必须可选字段，旧快照永不报错
